# ТЗ для Codex: доведение CRM_system до полного рабочего MVP

Мастер-задание для оркестратора Codex и его агентов. Каждый эпик `E*` — отдельная
задача (или серия задач) для одного агента. Порядок и параллельность — в разделе 6.

## 1. Контекст (прочитать перед любой задачей)

**Репозиторий:** `flycited2-dotcom/CRM_system`, рабочая ветка `codex/stage-0-1`
(текущий tip `5e9556a` развёрнут в продакшене). Прямые пуши в эту ветку запрещены —
только PR.

**Стек:** монорепо
- `apps/api` — NestJS + Prisma + PostgreSQL + Redis;
- `apps/web` — Next.js (App Router, TypeScript);
- nginx + Docker Compose (пять контейнеров: api, web, nginx, postgres, redis).

**Что уже работает (не сломать):** авторизация (JWT + refresh, work sessions),
users, clients + contacts + комментарии + файлы + история, leads (CRUD, назначение,
статусы, закрытие, конвертация в клиента). 17 unit-тестов зелёные, обе сборки проходят
после Prisma generate.

**Известные дыры (проверено на `5e9556a`):**
- `deals`, `tasks`, `offers`, `messages` — пустые модули-заглушки;
- конвертация лида в сделку возвращает HTTP 501;
- объявленная команда lint нерабочая — конфигурации ESLint 9 нет;
- CI нет; публичных webhook'ов, почты и Telegram-уведомлений нет.

**Документация — источник истины** (лежит в `docs/specs/` репозитория; если её там
ещё нет — см. задачу E0.1):
- `01_TZ_CRM.md` — главное продуктовое ТЗ (модули, поля, статусы, MVP);
- `02_ARCHITECTURE.md`, `05_DATABASE_SCHEMA.md`, `06_API_SPEC.md` — техника;
- `03_ROLES_ACCESS.md` — роли и матрица доступов;
- `04_BUSINESS_PROCESSES.md` — процессы (правило 15 минут и т.д.);
- `07_UI_UX_SPEC.md` — экраны;
- `08_DEVELOPMENT_ROADMAP.md` — этапы; `09_ACCEPTANCE_CHECKLIST.md` — приёмка;
- `10_DEVELOPER_INSTRUCTIONS.md` — обязательные инженерные правила.

**Эталон визуала:** статический прототип на 45 экранов — репозиторий
`flycited2-dotcom/ClaudeDesign_tehnika_site`, ветка `codex/parsing_tenders`.
Ключевые файлы: `assets/css/tokens.css` (палитра, шрифты, тени), `assets/css/app.css`
(30+ компонент-классов), `app/dashboard-owner.html` (эталон языка), `ONBOARDING.md`
(правила визуального языка). Реальный фронтенд должен сойтись с прототипом.

## 2. Цель и критерии успеха

**Цель:** довести CRM до критериев готовности MVP из `01_TZ_CRM.md` §7 — с чистым
кодом, полным RBAC, единым визуальным языком и готовыми точками подключения
интеграций (сайты, почта, Telegram, тендер-парсинг).

**Успех проверяем так (observable):**
1. `lint`, все тесты и обе продакшен-сборки зелёные локально и в CI.
2. Каждый пункт чек-листа `09_ACCEPTANCE_CHECKLIST.md` для этапов 1–8 проходит.
3. Сквозной сценарий работает через UI: лид с webhook'а → назначение менеджеру →
   конвертация в сделку → задачи → КП (PDF) → смена этапов воронки → закрытие;
   каждая операция видна в activity log и подчиняется ролям.
4. Grep-чек запрещённых UI-паттернов пуст (см. §3, «UI-правила»).

## 3. Глобальные правила для всех агентов

**Workflow.**
- Ветка `codex/<epic>-<короткий-slug>` от актуального `codex/stage-0-1`; PR туда же.
- Один PR — одна связная задача. Стремиться к diff ≤ ~600 строк без учёта
  сгенерированного кода и снапшотов; крупные эпики резать на серию PR.
- Канонические команды проверки бери из `package.json` (корень и `apps/*`).
  E0 фиксирует их в `README` и CI — после этого расхождения с README считаются багом.

**Инженерные правила (из `10_DEVELOPER_INSTRUCTIONS.md`, обязательны).**
- Роли и права не хардкодить; guards на каждом эндпоинте; UI строится с учётом роли.
- Статусы — кодовые значения в БД (`new`, `in_progress`, …), русские названия в UI.
- Вся бизнес-логика на бэкенде; frontend не принимает решений.
- Файлы не хранить в БД; физическое удаление данных запрещено — только soft delete.
- Все значимые действия — в activity log (создание, изменение, смена статуса,
  назначение, отправка КП, вход/выход, ошибки интеграций).
- DTO-валидация на каждом входе; нет endpoint'ов без авторизации, кроме явно
  публичных (webhook с токеном, health).
- Уведомления — только через единый `NotificationService` + события + канальные
  адаптеры. Модули напрямую в каналы не пишут.
- Миграции Prisma аддитивные, применяются на чистой базе; seed идемпотентный.
- Секретов в git нет. Все внешние параметры — через env с примером в `.env.example`.

**UI-правила (из прототипа, обязательны).**
- Дизайн-токены и компонент-классы переносятся из прототипа; сырые hex-цвета и
  дефолтная палитра Tailwind в разметке запрещены.
- Запрещённые паттерны (grep должен быть пуст): `transition-all`, `indigo-`,
  `blue-5`, `blue-6`, `green-5`, `emerald-`.
- Шрифтовая пара прототипа: serif для заголовков/KPI, sans для текста, mono с
  `tabular-nums` для сумм и ID.
- Деньги и даты — только через общие утилиты форматирования («1 240 000 ₽»,
  «3 ч назад»), не ручной вывод.
- Анимации — только `transform`/`opacity`, 150–200 мс.
- У каждого кликабельного элемента есть hover, focus-visible и active состояния.

## 4. Definition of Done — каждая задача

PR не считается готовым, пока в его описании нет фактического вывода команд:

1. Lint зелёный (после E0 — обязателен всем).
2. Все тесты зелёные: существующие + новые на добавленную логику. Установка
   владельца: тяжёлые e2e-фермы не строить, но unit/integration-тесты на свою
   бизнес-логику (сервисы, guards, конвертации, расчёты) обязательны.
3. Обе продакшен-сборки (`api`, `web`) проходят.
4. Если менялась схема БД: миграции применяются на чистой базе, seed проходит.
5. Если менялся UI: скриншот(ы) экрана в PR + пустой grep-чек.
6. Заполнен шаблон отчёта из §9.

## 7. Вне рамок (scope OUT — не делать)

- Интеграция с 1С (этап 11) — только не закрывать для неё дверь архитектурно.
- MAX, WhatsApp, телефония — только адаптерные интерфейсы, без реализации.
- Складской учёт, резервы, счета, бухгалтерия — зона 1С.
- Мобильное приложение, GPS, скриншоты сотрудников, AI-автоматизация.
- Инфраструктура продакшена: домен, HTTPS, DNS, деплой, секреты, бэкапы — делает
  оператор вручную, агенты в прод не ходят и env-файлы прода не трогают.

## 8. Вводные, которые владелец даст позже

До их появления функциональность строится на env-конфигах, флагах и моках —

## 9. Если данных не хватает (escape hatch)

Агент столкнулся с противоречием документации, отсутствующей вводной или
недоступным ресурсом → **не изобретать**:
1. Пометить PR как draft, в описании раздел `BLOCKED:` с конкретным вопросом
   (что нужно, для чего, какие варианты).
2. Продолжить независимую часть задачи, если она есть; иначе завершить задачу
   как draft и отчитаться.
